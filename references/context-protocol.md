# Context store protocol (since v3.11.0; repositories and provider blocks since v3.13.0; slots, the cascade and `explain` since v3.15.0; search since v3.16.0)

The user's context can live as **records** — one markdown note per section of `local-context.md` — in a **context store**. `local-context.md` then becomes the **compiled view** of the records: skills read it exactly as before, and anything written into it directly (by a skill, another plugin, or the user in Obsidian) is imported back into the records. The deterministic `ctx` command line (`scripts/ctx.py`) migrates a single-file context losslessly, snapshots before every change, keeps a journal and generates a **context card** (`INDEX.md`). A user who never migrates keeps working exactly as before.

## 1. Where things live

- **Store:** `{storage_root}/_System/context/` — `storage_root` as in `persistent-storage.md`: the first vault in `## Obsidian Vaults` whose sync mode is not `off` → `{vault_path}/{plugin_folder}`; otherwise `~/.grow-pm`.
  ```
  _System/context/
  ├── INDEX.md              # the context card, generated
  ├── records/<id>.md       # one record per section
  ├── sync/                 # since v3.14.0: the daily sync's reports, YYYY-MM-DD.md — written to be read in Obsidian
  ├── search/
  │   └── golden.yaml       # since v3.16.0: your golden set of the search — ctx only reads it (§5g)
  └── .state/
      ├── compiled.json     # hashes of the last compile: per record and per section of each compiled copy
      ├── journal.jsonl     # one line per change
      ├── slots.json        # since v3.15.0: what you decided about slots — bindings, names, preferences, answers (§5f)
      ├── search.json       # since v3.16.0: your choices in the search's block of variants (§5g)
      ├── entities.json     # since v3.18.0: your answers — two cards are, or are not, the same entity (§5h)
      └── blocks/           # since v3.13.0: what the store remembers of each repository's blocks (§5e)
          ├── <repo>.json   #   when it was checked and, per block, its base hash, version, host record
          └── <repo>/<sha>.md   # the base texts
  ```
- **The sync reports** `sync/YYYY-MM-DD.md` (since v3.14.0): one note a day, written by the daily sync only when a pass changed something, decided a conflict or tripped a safeguard (`context-provider-protocol.md` §12.11). They are notes for you, not records: `status` and `validate` do not count them as stray files, a snapshot does not hold them (so `ctx undo` leaves them as they are), and a report older than 90 days moves to `~/.grow-pm/trash/` (30 days there).
- **Compiled copies:** `~/.grow-pm/local-context.md` (the canonical one — the digest, the hooks and Step 0a find it) and, when `storage_root` is a vault, `{storage_root}/_System/local-context.md`. `ctx compile` writes both; with a store, `ctx` replaces the manual vault-mirror copy of `local-context.md`.
- **Snapshots** `~/.grow-pm/snapshots/` and the **lock** `~/.grow-pm/.ctx.lock` — outside any vault.
- **The search's section index** `<home>/.grow-pm/index/` (since v3.16.0; `<home>` is the one `ctx` takes, `--home`): `sections.sqlite` (schema `search-index/1`), `index.json` (its state — the session digest reads only this), `index.lock` (one refresh at a time) and `last.json` (the ids of the last searches, for `search --get` and `search remember`). Outside every vault, so iCloud never syncs it; a cache rebuilt from the files — no snapshot, no journal line, no `undo`, and deleting the folder is safe (`ctx index rebuild`).
- **The golden set** `{store}/search/golden.yaml` (since v3.16.0, schema `search-golden/1`): your file, visible in Obsidian. `ctx` only reads it, no snapshot holds it (so `ctx undo` never takes back your edits in it, as with `sync/`), `status` and `validate` do not count it as a stray file, and the section index does not index it (§5g).
- **The digest's summary** `~/.grow-pm/.ctx-summary.json` (since v3.13.1): the store's counts as the session digest last saw them, for a session start that cannot count them in time (§7). Only beside a context file in a `.grow-pm` folder — never in a folder of the user's own; a cache, never a source of truth.
- There is no pointer file: `ctx` finds `local-context.md` like the digest does (`GROW_PM_CONTEXT_PATH`, then `~/.grow-pm/local-context.md`), derives `storage_root` from it and checks for `{storage_root}/_System/context/.state/`.

## 2. Records

**Split rules.** The file is cut into consecutive fragments that cover every byte exactly once, so the compile gives the file back byte for byte:

1. Everything before the first `## ` heading → the `header` record (the `#` title, `> Generated … Updated …`, `> Configurator version`).
2. Every `## ` heading starts a top-level record that runs to the next `## `.
3. Inside `## Organization: …`, every `### Product: …` and `### Team: …` starts its own record, running to the next `### Product:`, `### Team:` or `## `. Other `###` and deeper headings stay in the fragment they are in.
4. Headings inside fenced code and inside managed regions (`<!-- ns:begin … -->` … `<!-- ns:end … -->`) never split; a region stays in its record's body. **Except:** a region whose begin marker is followed, after blank lines only, by a `## ` heading starts a new fragment at its marker — the section the region wraps becomes its own record, titled by that heading.
5. `### Product:` outside `## Organization:` (for example under `## Landscape`) does not start a record.

**Types.** `User Profile` → `profile`; `Onboarding Status` → `onboarding`; `Organization: X` → `org`; `Product: X` → `product`; `Team: X` → `team`; a heading that starts with `Judgment`, `CJM Configuration`, `Knowledge Library`, `Templates`, `Obsidian Vaults`, `People`, `Planning`, `Focus`, `Release`, `Terminology & Style`, `Landscape`, `Experiments`, `Feedback` or `Custom Sections` → `setting`; any other `##` → `custom` (kept as is — for example a section another plugin writes).

**The record file** `records/<id>.md`:
```markdown
---
ctx: 1
id: "product.zorg-app"
type: "product"
title: "Product: Zorg App"
parent: "org.zorg"
order: 50
owner: "user"
source: "migrated"
modified: "2026-10-20T10:00:00+03:00"
sha: "<sha256 of the body>"
---
### Product: Zorg App
- **Jira Project Key:** PROJ
```
- The body is the section's exact text, blank lines included; the frontmatter is closed by the first `---` line.
- `id` = `type.slug` (`header`, `profile`, `onboarding` have no slug); the slug comes from the heading (Cyrillic transliterated), a repeat gets `-2`. An id never changes, even when the heading is renamed; the file name is the id.
- `order` steps by 10; the compile sorts by it. `parent` links products and teams to their organisation.
- `owner` is `user` or `plugin:<name>` — informational in v3.11.0: migration sets `user`, the user marks another plugin's section in the record's frontmatter.
- `source` is the kind of the last change: `migrated`, `import:home` / `import:mirror`, the command that made it (`ctx-set`, `ctx-append`, `ctx-add`), or the name the writer passed with `--source`.

## 3. The `ctx` command line

`python3 "<plugin root>/scripts/ctx.py" <command> [options] [--context PATH] [--store DIR] [--home DIR]` (the three path options go after the command; `--store` only for reading commands).

With several products and no `--product` the slots of a product and of a team are held back and one line names the products (exit 0). An unknown id, note or section, a file not read in time, or a file not downloaded that no local index holds (`файл не завантажено з iCloud: <шлях> — відкрий його в Obsidian або ctx index rebuild --download`; outside the plugin folder `… — відкрий його в Obsidian` alone) → exit 3; the server did not answer → exit 5 |

Exits 0, or 5 when a repository is unavailable |
| `provider apply [REPO] [--product P] [--choose BLOCK=theirs\|mine\|both [BLOCK=… …]] [--add BLOCK [BLOCK …]]` | one pass per repository: what needs no answer is applied and your edits stay; a `⚠` or `?` waits for `--choose`, a `+` for `--add`. A snapshot, the records, the block state, one journal line, the compile. Since v3.14.0 `--choose <block>=theirs` also takes the repository's text for a `✎`, and a text you rejected by undoing a pass of the daily sync (§8) is held — `утримано` — unless you take it the same way |
| `provider sync [REPO] [--if-due] [--now ISO]` | the daily sync (since v3.14.0; `context-provider-protocol.md` §12.11): `provider apply` with the answers given in advance, for the repositories whose registration says `sync: daily` — naming one that does not, or a paused one, is exit 3. `--if-due` keeps the repositories that are due (a day after the last successful check, an hour after a failed attempt), read from their block state alone — no lock, no network — and prints only the `CTX_RESULT` line when none is. A lock held by another session ends it at once with nothing done, and so does a registration still downloading. The edits waiting are imported first; the whole run takes 20 s at most. One line `Ядро оновило <N> блоків у <repo>, конфліктів <K> (лишено твоє) — звіт: <path>` per repository whose pass changed a block or decided a conflict. It exits 0 whatever the repositories did (3 for a bad call); `CTX_RESULT` holds `synced` (the ids) and `results` (one object per repository: `repo`, `at`, `outcome`, `updated`, `added`, `removed`, `kept_yours`, `took_rule`, `awaiting`, `held`, `rejected`, `reason`, `report`, `snapshot`; no `results` when nothing was due), and `skipped` — `busy`, `lock: <why>` or `guard: <why>` — when the lock or the guard stopped the run |

**Rules every writing command follows:** take the lock (a live lock younger than 120 s → refused; an older one, or a dead process's, is taken over); refuse a store that lies inside a registered provider's folder (`context-provider-protocol.md` §7); import direct edits first; snapshot; write each file atomically (a temp file, then rename); add a journal line; compile; drop trash entries older than 30 days. **Write allow-list:** every write or delete target, after its links are resolved, lies under `~/.grow-pm/` or the storage root; anything else → exit 4 and nothing written. `undo` writes only the current copies and store — never a path from a snapshot's manifest. A compiled copy is never replaced or created without a snapshot and a journal line — a compile with nothing to import that still rewrites a copy (a mirror without a baseline, a missing mirror) takes its own. Files are read within a time budget (30 s in all, `GROW_PM_CTX_READ_TIMEOUT`): a record that does not arrive — an iCloud-evicted file still downloading — stops the run with exit 3, naming it, before anything is written; since v3.14.0 so does a file the snapshot copies. **Since v3.14.0** the provider registrations are read on a shared deadline — three seconds each and six for all of them — and a registration not read in time (an iCloud file still downloading) may be the very provider whose folder holds the store, so the provider boundary cannot be checked: a writing command is refused (exit 4, `a registration could not be read: <path> — the provider boundary cannot be checked; try again when it has downloaded`) and the daily sync does nothing (`skipped`: `guard: <why>`); an unopenable or broken registration file is left out as before. `provider apply` checks an answer that names no block of the plan — a mistyped block, or a repository in the place of one — before the lock and before anything is imported (exit 3). A temp file a write cut short left in `.state/blocks/` or `sync/` is removed once it is 24 h old. **Since v3.13.0:** `provider adopt --apply` imports first like every writing command (so `ctx undo` across an adopt never takes back an edit made before it), then writes only the block state `.state/blocks/**` (after a snapshot) and the card's `Repos` line — no record of its own; `provider plan` and `repo …` write nothing and take no lock. **Since v3.15.0:** `slot …` imports first like every writing command, then writes only `.state/slots.json` (after a snapshot) — no record, no copy, no compile; `read` and `explain` write nothing, create no directory and take no lock. **Since v3.16.0:** `search remember|forget` do the same with `.state/search.json` (since v3.18.0 `entity same|not-same` with `.state/entities.json`); `search` (with `--get` and `eval`) and `index` take no store lock, import nothing and write only `<home>/.grow-pm/index/`, already inside the allow-list. `provider apply` follows the rules above once per repository: every repository is read first, and one that is unavailable — unreachable, or a blocks file that is empty, cut, foreign or holds none of the blocks you have a base for (`context-provider-protocol.md` §12.2) — stops the run before the lock, with nothing written.

**Output contract.** The last stdout line is `CTX_RESULT {json}`; a conflict prints `CTX_CONFLICT {json}` (each conflicting record with the versions) right before it. **Exit codes:** 0 ok · 2 a decision is needed (`provider apply`: also when answers are awaited — the rest was applied) · 3 bad input, no store, an unreadable or missing record, a value outside its type, an unknown skill for `read` or `explain`, an unknown repository or block, an unknown slot, a slots memory that cannot be read (`slot …`; `validate` reports it as its error) (usage errors too) · 4 refused (managed region, provider boundary, busy lock, existing store, `undo` while edits wait, a target outside the allow-list, a `restore` onto a current id, `provider apply` with only refused blocks left) · 5 a repository is unavailable — unreachable, or its blocks file is no source — and nothing was written (`provider` commands; for `search`, no source answered; `repo status` reports it and exits 0; `provider sync` never exits 5 — an unreachable repository is its outcome `unreachable`, and the command exits 0 whatever the repositories did, 3 for a bad call). The `provider` result shapes: `context-provider-protocol.md` §12.7; the plan signs: `context-provider-protocol.md` §12.5.

## 4. Direct edits — `sync`

Each compiled copy is cut with the same rules and compared, section by section, with the hashes of the last compile:

- **Changed section**, record unchanged since the last compile → the record takes the section's text.
- **New section** → a new record, placed after the record that precedes it in the file.
- **Renamed section** — a heading disappeared and, after the same preceding record, a new one appeared whose text holds at least half of the old record's non-empty lines → the same record, new `title`, same `id`. Otherwise: a removal plus a new section.
- **Reordered sections** → the records take the file's order (the canonical copy's, when both copies moved sections).
- **Removed section** → the record goes into the snapshot and leaves the store (`ctx undo` brings it back); it is always reported. **Three or more removals in one run** are a conflict until `--accept-removals`.
- **A record file missing on disk** (not downloaded yet, not synced yet, or deleted in Obsidian) → nothing is compiled and both copies stay as they are; `ctx` exits 3 naming the files and the way back (let them download; restore them from Obsidian's trash or a snapshot). `--accept-removals` drops them for good.
- **Conflict** — the only case that asks: the same section changed in a copy and in the record (edited in Obsidian), or differently in the two copies. `ctx` exits 2 with both versions; the caller shows them, asks which to keep and re-runs with `--resolve <id>=file` or `--resolve <id>=record`. `file` is the canonical copy, `~/.grow-pm/local-context.md`: to keep the vault mirror's version, or a merge of the two, put that text into the canonical copy first.
- A record edited directly in Obsidian, with no change in the copies, is simply compiled out.
- A copy with no baseline in the state (a mirror that differed at migration) is never a source of edits; the next compile rewrites it, after a snapshot and with a journal line.

## 5. Who writes

`local-context.md` stays the surface for edits; no skill has to learn record files.

- **Context Enrichment** (`local-context-protocol.md`), the **configurator** and **context-connect**: after saving `local-context.md`, when the session digest shows a `context: records …` line — on a host without the digest (Codex CLI): when `{storage_root}/_System/context/.state/` exists — and SHELL is available, run `python3 "<plugin root>/scripts/ctx.py" sync --source <writer> --reason "<what was saved>"`; exit 2 → show the two versions, ask, re-run with `--resolve`; no store or no shell → nothing more.
- **Other plugins** that write their own section — unchanged; the next `ctx` run imports their edits.
- **Hosts without SHELL** edit `local-context.md` as before; the next `ctx` run on a host with a shell imports the edits.
- **Moving in** is offered by the configurator — the Update item "Move my context to records" and one question at the end of onboarding — with one confirmation; `ctx undo` right after it moves back.

## 5a. What a skill reads — `ctx read` (since v3.12.0)

`references/context-manifest.yaml` says, for each skill, what Step 0c needs: from the active product and its teams, fields (a `- **Field:**` line, or the `#### Field` subsection when there is no such line) and `####` subsections; settings by the start of their title, read whole; `required` and `required_settings` mark the obligatory ones. Every skill also gets the User Profile and `Judgment`. The configurator and context-connect are `full: true` — they edit `local-context.md` and read it whole. Validator check 16 keeps the manifest in step with the skills and with "Which Skills Read What".

**Your own sections (since v3.12.1).** The manifest cannot name a user's own sections, so a `custom` or `setting` record says itself who reads it: `read_by` in its frontmatter — `all`, or skill names (`ctx assign`, or the Obsidian property as a list). `ctx read` adds such a record whole for those skills. A `custom` record without `read_by` is named in one line — `Власні секції без призначення: <title> (<id>), … — ctx get <id>, якщо запит їх стосується` — and the skill reads it with `ctx get` when the request is about it. Output over 8 000 tokens ends with `⚠ ≈N токенів — більше за 8000; найбільший запис: <id> (≈M)`; trimming is the user's call. `validate` and `status` list the unassigned `custom` records; the configurator's Update item "Who reads custom sections" assigns them.

`ctx read --skill S [--product P]` prints the card, then one block per record headed `## <title> · <id> · перевірено <date>`, with `⚠ застаріле (TTL N д)` or `⚠ неактуально: <reason>` when that applies, and one closing line `Відсутнє: …` — `(обов'язкове)` marks the obligatory ones; defaults apply to the rest. Since v3.14.1 a subsection the manifest names and nobody has is listed there too (never as obligatory), and when a skill reads several teams, what one of them lacks is named with it — `Members (Team: Beta)`. A subsection is also found under the other headings the engine knows for it (`ctx_store.SECTION_ALIASES`): `Members` under `Team Members`, your own text still before any block; the card counts a team's members under either heading. Edits not imported yet, and a record missing on disk, are read from the canonical copy with a note (`ctx sync`). Archived records never appear. With several products and no `--product` (or an ambiguous one) the output is the card and the product list — the skill asks (Step 0d) and runs again. Step 0c of `local-context-protocol.md` says when a skill uses it.

**Slots (since v3.15.0).** A name the manifest reads from a product, a team or the profile that has a slot (§5f) is answered through the slot: your text and the blocks bound to it, wherever they sit, in the order of the cascade, each with the line that says whose it is. A slot nothing answers goes to the same `Відсутнє:` line and says where it looked — `Members (шукав: Members, Team Members, Склад команди, Учасники у Team: Beta (B); блоків із цим слотом немає)`; a bound block that exists but cannot be given to one team says `є нерозміщений блок — ctx explain <slot>` in place of `блоків із цим слотом немає`; a required field of a record read whole (the profile) is there only when that record has it — when only a block bound to its slot in another record answers, it is missing and says `є блок в іншому записі — ctx explain <slot>`; `missing` in `CTX_RESULT` keeps the short form of v3.14.1 (`Members`, `Members (Team: Beta (B))`). A name with no slot is read as before. What a slot of the view used from a bound block is not repeated in a record the same skill reads whole (§5f, *No duplicates*). Lines that say what could not be read (an unread registration, the slots memory, a block state; §5f) come before `Відсутнє:`; `CTX_RESULT` adds `slots` — for each slot the sources shown, the sources named in a «також» line and the sources that diverge.

**Blocks (since v3.13.0).** A field or a subsection is looked for in the record's own text first — outside the managed regions — and only then inside a repository's blocks. The text of a block is preceded by the line `> [<repo-id> · v<version> · станом на <date>]` (`context-provider-protocol.md` §12.9), so a skill states a fact from a block with its source and date. Since v3.15.0 this order holds for a name with no slot; a name with a slot is resolved by the cascade (§5f) — your text and every block bound to the slot are candidates — and a block bound to a slot says which one on the same line. A block that neither you nor its publisher bound to any slot (`ctx slot bind`, `slot=`) answers by its heading, as above, only in a product, team or profile record in which your text has nothing for the slot — unless the plugin's own `team#Members` gives it the slot's text (a team block whose heading reads `Team Members` still answers by name) — and its line says `за назвою, без прив'язки`. A record whose file and record disagree (a conflict waiting for `ctx sync`) is headed with `⚠ конфлікт: файл і запис різняться — ctx sync`.

## 5b. Lifecycle — invalidate, archive, trash, restore (since v3.12.0)

- **Invalidate** writes a `ctx` managed region right after the record's heading: `<!-- ctx:begin id=status -->`, `> ⚠ Неактуально з <date>: <reason>`, `<!-- ctx:end id=status -->`. The record stays in the copies, so even a skill that reads the file whole sees it; `status` in the frontmatter follows the region — remove the region and the record is current again.
- **Archive** moves the record file to `{store}/archive/<year>/<id>.md` with `status: archived`, the date, the reason and `former_after` (its predecessor). It leaves both copies; `assign_ids` treats its id as taken. The card counts the archive.
- **Trash** — `~/.grow-pm/trash/<time>-<id>.md`, outside any vault, 30 days: every record a sync removes (a section deleted from the file; a record missing on disk dropped with `--accept-removals`, its text taken from the canonical copy).
- **Restore** — an invalid record becomes current; else the archived record, else the newest trashed one comes back after `former_after`, else after its last sibling, else at the end. The body and both copies come back byte for byte.

## 5c. Typed fields (since v3.12.0)

`references/context-fields.yaml` declares the types of the fields the card and the skills read — `Role`, `Role scope`, `Level home`, `Email` in the profile; `Jira Project Key`, `Confluence Space`, `Platforms`, `Locales`, `URL` in a product; `Mode`, `Deferred steps` in onboarding; the `Judgment` switches. Types: text, enum, list, key, url, date, email, int. The text line stays the source of truth (a `list` may be the bullets under `#### Field`); `validate` warns about a mismatch, `set` refuses one, `get --json` returns the parsed value. An active record carries no `status` key; Obsidian properties a user adds to a record's frontmatter are kept.

## 5d. Freshness (since v3.12.0)

Each record has a `verified` date — set by every write of it through `ctx` (an import, `set`, `append`, `add`, `restore` — not `assign`, which changes only who reads it), by an Obsidian edit of it being picked up, and by `ctx verify`; until then the store's first v3.12 run (`freshness_since`). Default TTL: product and team 90 days; organisation, profile and settings 180; the header, onboarding and custom sections none — `ttl_days` in the frontmatter overrides (`0` = never stale). A stale record: the digest counts it (`· K stale`), the card marks its row (`⚠ <date>`), `ctx read` marks its block, `status` and `validate` list it. A skill states a fact from a stale record as "станом на <date>" and never asks about it mid-run; `ctx verify --stale` or the configurator's "Review stale records" confirms.

## 5e. Provider blocks (since v3.13.0)

A repository's context blocks (`context-provider-protocol.md` §12) are managed regions inside the records. The registrations a store draws them from are listed by `ctx repo list`; `ctx provider plan` compares each block with the repository's text and with the **base** the store remembers, and `ctx provider apply` merges them. What the store remembers lives in `.state/blocks/` (§1), is kept by snapshots, and is brought back by `ctx undo`.

- **Human edits in a block are kept.** An edit inside a block — in `local-context.md`, or in a record file in Obsidian — is imported like any direct edit (§4). Every later refresh keeps it: the plan reads the block as `✎` when the repository did not change it, and asks (`⚠`) when the repository did.
- **Agent edits are not written.** `ctx set` and `ctx append` refuse a target inside a managed region (exit 4), and a skill or the agent never writes inside one by any other path (`vault-schema.md` → Generated regions and layers) — a text typed into a block of `local-context.md` is imported as a human's edit and kept as one. The only writer of a block's text is `ctx provider apply` — for a block the user did not touch (`~`, `−`) or for the answer the user gave (`--choose`, `--add`) — and the record it writes carries the `source` `repo:<id>`.
- **A source that cannot be trusted removes nothing.** A blocks file that is empty, cut, another repository's, or holds none of the blocks you have a base for makes the repository unavailable (exit 5, nothing written) — never "every block removed"; a source behind your base (a lagging copy) is `=` and never takes a block back a version (`context-provider-protocol.md` §12.2, §12.5).
- **Nothing is written to a repository.** `ctx` reads a core folder or a server and writes only under `~/.grow-pm/` and the storage root.
- **The daily sync is the same merge without a person at the keyboard** (since v3.14.0; `context-provider-protocol.md` §12.11). It runs only for a repository whose registration says `sync: daily` — the one opt-in, given once per repository by a yes in the connect flow — and answers every row by the cascade: your text wins a conflict unless the core marks the block `policy=rule`; a `?` is left waiting unless the block is a rule (then the core's text); more than one block removed by the core in a pass is held. Every pass that changes something has a snapshot and a journal line (`provider-sync`), and a pass worth reading — one that changed something, held a removal or failed in a way you should see — a report in `sync/`; `ctx undo` takes it back and the sync does not apply that text again.
- **Bases come first.** A context that already holds a repository's blocks has no bases; `ctx provider adopt` sets them (§12.4 of the provider protocol) so that the first plan does not ask about every block.

## 5f. Slots, the cascade and `explain` (since v3.15.0)

A **slot** is the place in a record where an answer to a question lives: `team.members` is "who is on the team" whatever the heading says — `#### Members`, `#### Team Members`, `#### Склад команди` — and whether the text is yours or a block a repository put there. A skill asks for the slot; the resolver (`scripts/ctx_resolve.py`) finds every text that may answer it, decides by the cascade which one the skill gets, says whose it is and names what it did not find. The point of the version is visibility: for each piece of context a skill gets, it is known where it came from and why it won. The resolver only reads — `ctx read` and `ctx explain` take no lock, use no network and write nothing; what you decide about slots is kept by `ctx slot …` (below).

**The catalogue.** `references/context-slots.yaml` (`schema: context-slots/1`) lists the slots. Each has:
- `id` — `<record>.<name>`, never changed once shipped (`product.key_metrics`, `org.key_metrics`);
- `kind` — `value` (one line, one answer: a key, an address), `text` (prose or a table, read whole) or `list` (items, one per bullet or row);
- `record` — the kind of record the slot is looked for in: `product`, `team`, `profile` or `org`;
- `names` — the headings and field names the slot answers to, English and Ukrainian; the first is the name the manifest uses, and a manifest name finds its slot without regard to case. A heading is matched without regard to case and may carry a qualifier after the name (`Key Metrics (focus)` answers `Key Metrics`) — the rule `ctx read` always used; a field line is matched by its exact name, as before;
- `about` — one Ukrainian line on what the slot holds; it is printed beside the text of a block bound to the slot.

The manifest does not change: it names fields and subsections, and the resolver translates each name into its slot through the catalogue, in the manifest's lookup mode (`required` and `fields`: the field line, else its subsection; `sections`: the subsection only). A name with no slot is read as in v3.14.1. Validator check 16 keeps the files in step: every name the manifest reads from a product, a team or the profile has a slot, every slot has a kind, a record, a name and an `about`, and two slots of a record never share a name. The catalogue holds general slots only — never a company's own block ids.

**Candidates — what may answer a slot.**
1. *Your text* — in the records of the slot's kind (the active product for a `product.*` slot, the teams of that product the skill reads for a `team.*` slot, the organisation, the profile), outside the managed regions. One candidate per record: under the first of the slot's `names` that answers, in the catalogue's order, else under a heading you mapped to the slot (`ctx slot map`). A heading you mapped to another slot is not a name of this one — your explicit mapping beats a name of the catalogue (`Key Metrics (focus)` mapped to `product.okrs` is no candidate of `product.key_metrics`).
2. *A bound block* — a block of a registered repository tied to the slot by a **binding**, in whichever record it sits. A guess from a heading never binds a block (`Key Metrics` of a company's plan and `Key Metrics` of a product are two slots); `ctx validate` only proposes one (below). Per block the first binding found counts, and the others do not apply to it:
   1. yours — `ctx slot bind` (`.state/slots.json`);
   2. the publisher's — the attribute `slot=<slot>[,<slot>…]` in the begin marker of the block, read from the text the core gave last (the block's base in `.state/blocks/`), never from your region (`context-provider-protocol.md` §12.2). A block with no base has none; your own binding works without one;
   3. the plugin's — for every registration the `team` block's `Members` subsection answers `team.members` (`team#Members`) and nothing else of that block: its `jira_project_key` and `jira_team_field` lines are not bound: the core's `jira_project_key` line can carry more than the product's own key (the team's other projects, when the team has more than one), so its value can differ whatever the label, and a bound line would then add a «також» to every skill that reads the key; `jira_team_field` is a team's name, not a Jira Team ID.

   A binding to a slot the catalogue lacks — a publisher ahead of the plugin, a slot your memory names that this catalogue has not — is no binding (since v3.15.2): it binds nothing and sets no other source aside, so the next one in this order binds the block, and `explain` and `validate` name it (`unknown`); a block bound only so may answer by name (candidate 3), and like any block with a binding it is not proposed again nor listed with the blocks no slot takes — the `unknown` line says what is wrong with it. A publisher's `slot=` that your own binding of the same block set aside is ignored (your binding wins for the whole block); `explain` and `validate` name it. A binding to a block that is in none of the records — the core took it away, or it was never added — stays in the memory and has no candidate; `explain` and `validate` say `прив'язка до блоку, якого немає в записах`, nothing fails.

   *The text a bound block gives:* a binding with `#Subsection` — that subsection, up to the next heading of the same or a higher level; a block bound to several slots — for each slot the part that answers that slot's names (none: the binding is invalid and `validate` says so); otherwise the whole block. A `value` slot takes the field line inside that text that answers its names; a block without such a line is no candidate for it. A block that is not one sound region (a repeated id, nested blocks, a broken marker — `context-provider-protocol.md` §12.1) gives nothing through a binding.

   *Whom a bound block belongs to:* a block in a product's or a team's record belongs to that product or team. For a `product.*` slot, and for a `team.*` slot whose binding names no team, a block in another product's record is no candidate; a block in a team's record answers only while that team is read (a `product.*` slot gets it for the active product); a `team.*` slot's block in the active product's own record needs exactly one team or a binding that names the team, else it is unplaced. In a `custom`, `setting` or `org` record a `product.*` slot gets it for the products its repository serves (`products` in the registration, empty — all; a registration not read — all), and a `team.*` slot only when the product has one team or the binding names the team record. A binding that names the team record (`--team <record id>`) places the block with that team wherever it sits, while that team is read. An `org.*` or `profile.*` slot takes the block from wherever it sits — another product's record too. A block that cannot be given to one team is **unplaced**: the skill does not get it, `explain` shows it with the command that places it and `validate` warns — a gap with an explanation is better than another team's members in a task.
3. *A block found by name* — what v3.14.1 did, kept: in a product, team or profile record where your text has nothing for the slot, the first block of that same record that has a subsection or a field under one of the slot's names — unless a binding of the block gives this slot its text (then it answers through that binding only, even where the binding does not place it), or you or the publisher bound the block to any slot of the catalogue (`ctx slot bind`, `slot=`). An explicit binding says what the block is, as a heading you mapped to another slot is no candidate of this one: a block you bound to `org.key_metrics` is never a `product.key_metrics` guess, and a binding of yours that finds nothing for its slot leaves a gap with an `увага:` line in `explain` and `validate`, not a guess. The plugin's own `team#Members` is no such word: a team block it finds nothing in (a heading `Team Members`) still answers by name, and `explain` shows it so. It stands at a repository's level and its line says `за назвою, без прив'язки`. So an upgrade with no binding loses no text a skill had.

**The cascade.** In this order:
1. *a core rule* — a bound block whose base says `policy=rule` (`context-provider-protocol.md` §12.2). It wins; your text for the slot is printed in full under it after the line `твоя примітка до правила` (a rule is annotated, never overridden), and every other candidate with another text is one «також» line. Of two rules the higher `rank` wins;
2. *yours*;
3. *the repositories by `rank`* (a higher one is stronger, `context-provider-protocol.md` §3b); at the same rank the repository id orders them;
4. *derived* — a value an agent derived from the connectors. The place is in the order; nothing writes it in v3.15 (the configurator as a loop, v3.19).

**A list of people — `team.members` — since v3.18.1** is one line per person in `ctx read` (`ctx_eslots.read_members`): the team record is matched with its team card by its name or the name without `(…)` — never what the brackets hold alone, a parent team or a product (a file name, title, slug or alias first, the team's normalised names only when none is exact; of several, the one card of a core's or your index before another team's card in a local index; else none, and two cards say the `ctx entity same "<a>" "<b>"` that would make them one — a record is no card, so this matches and never merges); the record's items (yours, a bound block's), the card's members (§5h: its list, its `Склад команди`) and the members derived from the cards (a person whose winning team is this one) are joined by entity — the item's link, its e-mail, else a name exactly one card carries (`за назвою`), else a name that in another spelling (`same_person`: transliteration, word order, a mark beside it) is that of exactly one person the list's other sources name (`схоже ім'я` — only within the list, never across the registry); a namesake or a name no card carries stays your text, never joined by its words. A line is the strongest source's row (yours first), its sources (`твоє`, a repository's id, `виведене`) and `лише виведене` when only the derivation names the person; another source's row that differs is `також: …`. The origin line of each source comes first (`> [твоє · <record>]`, a block's line with its marks, `> [картка <repo> · <path>]`, `> [виведене з карток людей: N]`), then the section's own heading and `склеєно за сутністю: N`; at most 20 people found only by derivation, then `ще N лише виведених — ctx entity …`. A source's lines that are no item — prose, sub-headings, notes — follow as they are, under `> [<whose> — інший текст секції]`: nothing of the section is lost. A team with no members of its own gets its card's. `ctx entity "<команда>" --slot team.members` gives the same composition: it reads the store's team records matched with that team too. A core rule for the slot, or your `prefer repo:<id>`, prints its list as before with `з карток ще N — ctx entity "<команда>" --slot team.members` (N: the people the cards name and the list does not); `prefer all` prints every candidate in full, as before. The index is read as it is — never refreshed, no lock, nothing written; busy (also mid-read) or not built: the list as before and `пункти не склеєно: <чому>`; no vault and no local index: the list as before, no line; a record no card matches: its own items joined and `команду «…» не зіставлено з карткою: <чому>`. A failure of the join never fails the read: the list as before and `пункти не склеєно: …`.

Your **preference** for a slot (`ctx slot prefer`) changes the order for that slot: `mine` (the default); `repo:<id>` — that repository's candidate wins even over your text (all of its candidates for a list; a rule still wins; a repository with no candidate for the slot changes nothing); `all` — every candidate in full, the rule first, no note and no «також».

How the winners combine depends on the kind:
- `value` and `text` — the winner in full; under it, for each other source whose text differs, one line `також: <repo або «твоє»> каже інакше — ctx explain <slot>`. A `value` slot compares the value after `**<label>:**`, not the whole line, so the same key under two labels is no disagreement; a `text` slot compares the text with line endings and trailing blanks normalised. Several blocks of one repository bound to one such slot: the first answers, the others lose (`перший з блоків <repo>`);
- `list` — every candidate in full, in the order of the cascade, each with its own line. Items are not joined: one person in two tables is two rows (entities and cross-links, v3.17). A rule still shows alone, your list as its note.

*A divergence* — a `value` or `text` slot, no text of yours, no rule, no preference or answer that settles it, and two or more repositories at the highest rank with different text. Nothing is asked in the middle of a skill's run: `ctx read` prints every tied candidate in full, each with its line, and once per slot `⚠ розбіжність між репозиторіями — вирішити: ctx slot decide <slot> <repo>` (`<repo>` is the first of the tied by id). The skill relies on all of them and names the sources. It is `context-connect` on a refresh and the configurator's Validate that ask, one screen for all divergences; the answer, `ctx slot decide <slot> <repo>`, is kept with a hash of the text of every side (for a `value` slot, of the value) and the day, and the question comes back once, when a repository publishes a new text. Different ranks are no divergence: the higher wins and `explain` shows who lost. One answer is kept per slot — a second `decide` for another product or team replaces the first.

*A registration that was not read* (an iCloud file still downloading) leaves its blocks' rank and rules unknown. Such a candidate takes no part in the cascade: it is shown in full after those that do, with no `перевага` mark. One line, printed once before `Відсутнє:` and not under each candidate, says `реєстрацію <файл> не прочитано — ранги й правила її блоків невідомі; кандидати з неї показано без каскаду` — only when a block in the records has a namespace no registration read has.

**What a skill sees.** Every candidate is printed with a line that says whose it is.
- A block: `> [<repo> · v<v> · станом на <date>]` (as since v3.13.0) and then, each after ` · ` and in this order: `слот <slot> — <about>` (a bound block: in a slot, the slot shown; in a record read whole, one for each slot the block answers); `за назвою, без прив'язки`; `з твоїми правками` (the region differs from every base the store keeps of it); `правило ядра`; `перевага: <mine|repo:<id>|all>` (when a preference shaped the answer; never on a candidate of a registration not read).
- Your text: `> [твоє · <id запису>]` — only when the slot shows more than one candidate or has a «також» line, a note or a divergence. Your text as the only candidate is printed with no line, as in v3.14.1.
- *No duplicates.* What a slot of the view used from a bound block is not repeated in a record the same skill reads whole (a `custom` or `setting` record through `read_by`, a setting the manifest names, a whole team): the record gets exactly what the slot used replaced — the whole region by `> [блок <block> — у слоті <slot> вище]` when the slot took the whole region; a subsection (a `#Subsection` binding — the plugin's `team#Members` among them — or the part of a block bound to several slots) by `> [блок <block> › <Підсекція> — у слоті <slot> вище]`, the rest of the region and its line staying; for a `value` slot nothing is taken away. A skill that does not ask the slot gets the record whole, as before.
- Lines before `Відсутнє:` that say what could not be read: the registration (above); `пам'ять слотів не прочитано (<причина>) — прив'язки й рішення не застосовано`; `стан блоків <repo> не прочитано — атрибути slot= і policy=rule його блоків невідомі`. A reader goes on without what it could not read.

For a skill that asks `team.members`, with your `Team Members` table and the core's `team` block, `ctx read` prints your table after `> [твоє · team.alpha-a]` and then the block's `Members` subsection after `> [zorg-core · v0.2 · станом на 2026-10-19 · слот team.members — склад команди: люди, ролі, контакти]`; under a rule it would print the rule first and, after `твоя примітка до правила`, your table.

**`ctx explain [SLOT …] [--skill S] [--product P] [--json]`** prints, from the same assembly `ctx read` uses, where each slot came from and why the winner won (a line under a header is indented by two spaces in the output):
- `team.members · список · Team: Alpha (A)`
  - `✔ твоє · team.alpha-a › Team Members · перевірено 2026-10-19`
  - `✔ zorg-core · блок team#Members v0.2 у записі team.alpha-a · станом на 2026-10-19 · прив'язка: плагіна`
  - `чому: список — виводяться всі кандидати; team.members у ctx read склеєно за сутністю`
- `product.key_metrics · текст · Product: Zorg App · не знайдено`
  - `шукав: Key Metrics, Ключові метрики — у Product: Zorg App; блоків із цим слотом немає`
  - `прив'язати свою підсекцію: ctx slot map product.zorg-app "<Назва>" product.key_metrics`

Reading it:
- The header is `<slot> · одне значення|текст|список · <record title>`, with `· не знайдено` when nothing answers. A candidate line starts with its outcome — `✔` won or shown (yours; a block with its repository, `блок <block>[#<sub>] v<v> у записі <record>`, `станом на <date>`, how it was bound: `прив'язка: твоя|slot= видавця|плагіна`, `за назвою, без прив'язки`, `з твоїми правками`, `правило ядра`), `✗` lost (`програв: <reason>`; one that says what a shown one says lost by saying it once), `⚠` repositories that tie (with `ctx slot decide`), `·` a block that cannot be placed (with `ctx slot bind … --team`). `чому:` is the cascade in words: `правило ядра` · `перевага: …` · `список — виводяться всі кандидати; team.members у ctx read склеєно за сутністю` · `твоє перемагає (блок не є правилом ядра)` · `більший ранг: <repo> <rank> > <repo> <rank>` · `рівний ранг <rank>, різний текст: <repos>` · `твоє рішення від <день>` · `єдиний кандидат` · `реєстрацію не прочитано — показано без каскаду`.
- A slot nobody answers says what it looked for — the slot's names and those you mapped, and the record — and prints the `ctx slot map` command; what the memory holds about a slot is shown with the `ctx slot forget` that takes it back (a decision whose texts changed since says `зараз не діє: тексти змінилися`); a binding that does nothing is an `увага:` line.
- `SLOT …` — only those slots, in the order given, none twice. `--skill S` — the slots S asks, in the order and the lookup mode of its manifest entry (a skill that reads the whole file asks none). Neither — every slot with a candidate, a note or something in your memory, then two lists: `Блоки без прив'язки` — regions of a registered repository with an id and no binding at all (the plugin's `team` counts as bound) and `Вимкнені блоки (skip_blocks) — ядро пропонує, ти вимкнув:`. A named or a skill's slot is explained for every place, found or not. With several products and no `--product`, the slots of a product and of a team are held back and one line says `Продукти: …`; the run still exits 0.

**What you decided — `.state/slots.json`** (schema `context-slots-memory/1`). It lives in the store, not in a record and not in a registration: a registration that did not parse would be dropped by this and older versions, and with it the guard of a provider's folder. It holds `bindings` (`repo`, `block`, `sub`, `slot`, `team` — one per repo, block, sub and slot), `aliases` (`record`, `heading`, `slot`), `prefer` (`slot` → `mine`, `repo:<id>` or `all`) and `decisions` (`slot` → `winner`, `hashes`, `at`). Every `ctx slot` command is a writing command: a snapshot, one journal line (`op: slot`, §8), and `ctx undo` takes it back, memory included — except one that changes nothing, which writes nothing. A key the loader does not know is refused, never dropped (a save would lose what a newer version wrote): a new key, or a new meaning of one, needs a new schema, `context-slots-memory/2`, never a `/1` file with one more key. v3.15.0 treats a `/2` file as a memory it cannot read (below): `ctx read` and `ctx explain` say so in one line, `ctx slot …` exits 3, `ctx validate` reports an error, and the file is never rewritten.
- `ctx slot bind <repo> <block>[#<Підсекція>] <slot> [--team <запис>]` — the block (or its subsection) of a registered repository answers the slot; `--team` (a `team.*` slot) names the team record it is for. Binding the same thing again changes nothing (`unchanged`).
- `ctx slot map <запис> "<Назва>" <slot>` — your own subsection, under a name the catalogue does not know, answers the slot; the record must be of the slot's kind.
- `ctx slot prefer <slot> mine|repo:<id>|all`.
- `ctx slot decide <slot> <repo> [--product P]` — the answer to a divergence, computed on the records as they are now; refused (exit 3) while a registration could not be read, for there is no rank to compare then.
- `ctx slot forget <slot>` — everything the memory holds about the slot.

A slots memory that cannot be read (an iCloud file still downloading, not JSON, another schema) is never reset: `ctx read` and `ctx explain` go on without it and say so in one line, `ctx slot …` stops (exit 3, `slots memory not readable|not valid: .state/slots.json (…)`), `ctx validate` reports it as an error and skips the other slot checks.

**`ctx validate` and the slots.** Reading only, every product when there are several. After the lines for what could not be read, one warning each for: a binding that does nothing (`slot binding: <repo> <block>[#<sub>] → <slot> — <why>`: a slot the catalogue lacks, a repository nobody registered, a block gone from the records, a block that is not one sound region, a block that gives its slot no text, a `slot=` of the publisher your own binding set aside) and a block that cannot be given to one team (with the `ctx slot bind … --team` that places it); a divergence between repositories (`slot <slot> diverges between <a>, <b> — ctx slot decide <slot> <repo>`); and a binding worth making (`proposal: ctx slot bind <repo> <block>[#<sub>] <slot>`). A proposal is made for a block of a registered repository that nothing binds and that is one sound region: its first heading that answers a slot's `names` (the name, or the name followed by a qualifier) proposes the whole block, a later one its own subsection (`<block>#<Підсекція>`). Only the headings are read — not the slot's `about`, not a field line. A block with any binding and the `team` block (the plugin binds it) are never proposed; a block in `skip_blocks` is not in the records, but one already there is proposed whether or not its id is listed. `CTX_RESULT` has the proposals as `slot_proposals`. `context-connect` (a refresh) and the configurator (Validate) show them, and the divergences, in one package each; a yes is `ctx slot bind …` for each proposal and `ctx slot decide …` for each answer.

**Not in v3.15.** Joining the items of a list (one person from two tables) — v3.17; a writer of derived values — v3.19; search across repositories (Step 0.5) — v3.16.0 (§5g). The sync of v3.14 is unchanged: the resolver reads what it wrote.

## 5g. Search — `ctx search`, your choices and the golden set (since v3.16.0)

Step 0.5 of every skill — bringing in what your base already holds about a request — is `references/search-protocol.md`; the engine is `ctx search` (§3), and how it merges sources is `context-provider-protocol.md` §5. What it means for the store:

- **The search does not touch the store.** `ctx search`, `--get` and `eval` read the vaults, the cores, a registered local index, your glossary, the block states and `.state/search.json`; they take no store lock, import no edits and write only `<home>/.grow-pm/index/` (§1) — the section index and `last.json`. The network is used only for the server of a repository whose folder is not on disk (`host-profiles.md` §4). `search remember|forget` write only `.state/search.json`. Without a store the search works all the same — over the vaults of `local-context.md` and the registrations — only without your choices and without the golden set (`eval` then needs `--golden`).
- **The section index does not index the store.** The records, the compiled copies, `INDEX.md`, the blocks files and `_System/providers/` are what `ctx read` gives at Step 0c (§5a); a slot's text never comes twice. A slot that `ctx read` names in `Відсутнє:` may be looked for by the search and offered in the block of variants — never filled silently: slots are filled by the cascade alone (§5f).
- **Your choices — `.state/search.json`** (schema `context-search-memory/1`). When the search was unsure, a skill ends with a block of variants; a number you answer is remembered as "for this request the right note is this one" (`good`), «не те» as "this one is not it" (`bad`). One hint per request and product: the request's stems (the same words in another order or form are the same request), the product, `good`, `bad` and the day. A later request whose stems are similar (Jaccard ≥ 0.6) and whose product does not differ weighs a `good` note × 1.5, marked `твій вибір від <день>`, and marks a `bad` one `ти казав «не те»` — never taken silently. The discipline of `.state/slots.json`: a key this version does not know is refused, never dropped (a new key needs `context-search-memory/2`); a file that cannot be read is never reset — the search goes on without hints and says `пам'ять пошуку не прочитано (…) — без підказок`, and `search remember|forget` stop (exit 3). Snapshots hold it, so `ctx undo` takes a choice back.
- **The golden set — `{store}/search/golden.yaml`** (schema `search-golden/1`): requests with their frozen `variants` (written once, so that level 1 is measured the same way between versions), a `class`, `good` (the first is the direct answer), `ok`, `bad`, `source` (`draft`, `reviewed`, `choice`) and `added`; `product` and `skill` are optional, and a row about what the base does not hold has `good: []` and the class `порожній`. It is your file: `ctx` never writes it, so `ctx undo` never takes back your edits in it. `ctx search eval` reads your choices as rows of the set (`source: choice`), and `--no-hints` measures without them — a choice strengthens its own answer; undoing a `remember` removes its row with it. `eval` measures level 1 without a model: the share of requests whose right answer is among the first 50 candidates (with the frozen variants, and with the request alone), MRR, a line per class, the empty rows; it writes nothing but the index. The model level — what a session's model takes, leaves and offers — is measured in an acceptance run, never by the plugin's users (`testing/search_agent_eval.py`).

## 5h. Who is who — `ctx entity` (since v3.18.0)

The cards of one person, team, mission, module, metric or work item are often in several places: your person note, a core's registry card, a card another team keeps that a local index of yours holds. `ctx entity` (`scripts/ctx_entity.py`) joins them into one entity and says who it is, where its cards are and who links to it. It writes nothing into a note.

- **Cards** come from the section index (`context-provider-protocol.md` §10: one identity row per note, links as written, Jira-key-shaped tokens) and from every registered local index — the notes of a card's type the section index does not hold, their frontmatter alone. A card's type: `people`/`person` → person, `team`, `mission`, `module`, `metric`, `epic`/`feature`/`project` → work.
- **Keys, the strongest first:** your answer `ctx entity same`; an equal e-mail; a bridge recognised by its shape — a field of exactly one link, whatever its name, to a card of the same kind in another source, with nothing against it (for people the e-mails, when both have one, are equal, else the names are alike; for a team, a mission, a module or a metric a name or an alias is shared; for work the Jira key is the same). A name or a title never merges two cards. `ctx entity not-same` keeps two cards apart whatever the keys say. A team linked under another name is `пов'язана з` it, not merged. A work card's bridge to a note of another source whose name carries the same key makes that note its second home (the core's page of an epic).
- **Maybe the same:** two cards of one kind from different sources whose names are alike (two work cards: the same Jira key) and that you have not answered are an open pair — never two people whose e-mails differ —, shown on both entities and by `ctx entity pairs`. Nothing reminds you of them.
- **A Jira key with no card** stays a mention: `ctx entity <KEY>` lists the notes that carry it — only for a key whose project prefix a card names (a team's or a mission's `…jira…` fields, a work card's key) or a `/browse/` link names; any other key-shaped text (`GPT-4`) is no key.
- **Who links to it** — every link resolved as `ctx search --get` resolves one (the exact path, the plugin folder's path, the end of a path, the name; several → none counted). A sensitive note (`data-policy.md` → Search, rule 1) is its title, path and day with ` · sensitive`; the field it links from only for a People-contour `--skill`; never its text.
- **The lines.** Several entities: `кілька сутностей «<запит>»:` and a line each, `<мітка> · <вид> — ctx entity "<шлях>"`. An answer `same` a `not-same` blocks, or one naming two kinds: `твою відповідь same <a> ↔ <b> від <день> не застосовано: …` (your answers apply newest first). A busy or unreadable section index has not answered: with nothing else to read, exit 5 `Базу не прочитано: …`, never «Не знаю».
- **A near match** (no e-mail, key, path, name or alias, only a name alike) starts with `схоже на «<запит>» — не точний збіг:`. A section index that did not answer (busy, damaged) never gives the bare «Не знаю»: `Поки не знаю «…» — <чому>`. A card whose file iCloud evicted before this build read its identity comes from a registered local index meanwhile.
- **Your answers — `.state/entities.json`** (schema `context-entity-memory/1`): `{"schema", "same": [[a, b, day]], "not_same": [[a, b, day]]}`, the two cards' paths in order. The discipline of `.state/search.json`: a key this version does not know is refused, never dropped; a file that cannot be read is never reset — `ctx entity` goes on without your answers and says `пам'ять сутностей не прочитано (…) — без твоїх відповідей`, and `entity same|not-same` stop (exit 3). Snapshots hold it, so `ctx undo` takes an answer back. `entity same|not-same` while the section index is busy say `індекс зайнятий — спробуй за хвилину; відповідь не збережено` (exit 5), a damaged one `Базу не прочитано: …` (exit 5) — never that a card it holds is no card.
- **Slots of one entity — since v3.18.1** (`scripts/ctx_eslots.py`, catalogue `context-slots.yaml`, `answered_on: cards`). One entity's answer has `слоти:` — a person's `роль`, `команда`, `e-mail`; a team's `склад`, `місії`, `батьківська команда`; a mission's `команди`, `проєкти Jira`; a module's or metric's `власник`. A card answers a slot by a frontmatter field of the slot's names, else — never on a person's card, which is a profile, nor on a sensitive note — by a section of those names (a list slot: every such section; `Місії (матриця …)` counts as `Місії`). A list item counts on a card only when it names an entity of the slot's kind — its first link, else its e-mail, else a name exactly one card carries — so a table of roles under `## Люди` is no member. **Derived:** a person whose *winning* `person.team` names a team is one of its members (never from a card that lost); a mission's `teams` and a team's `missions` answer each other. **The cascade** is the records' (§5): yours, then the repositories by rank, then a local index's card, then the derived; a value is the first, the others `також: <value> (<whose> · <path> · <day>)`, two cores of one rank with different values `різні значення: …`; a list is the union, one item per entity with every origin (`твоє`, a repository's or a local index's id, `виведене (<path>)`, `спірне` when two repositories dispute the person's team), `лише виведене` when nothing but the derivation names it, and the item's own row from the strongest card (yours first; another card's other row `також: «…»`). In CTX_RESULT a value answer has `origin` and `also`, a list answer `items` (each `origins`, `rows`, `kind`). A sensitive team's, mission's, module's or metric's card gives outside the People contour its members' names and sources alone — no row of its text, no value. `ctx slot prefer|decide|bind|map` do not reach a card's slot (your decisions are kept per slot, not per entity): they say the cards' cascade decides it. Outside the People contour a person's slots are the identity alone — role, team, e-mail — nothing of a profile is read.
- **`--slot <id>`** (repeatable) keeps those slots alone, with no `хто посилається` and no mentions — what a skill asks for (`--slot person.role --slot person.team`); a slot asked for and not answered is `<name>: —`; an unknown one is exit 3 with the slots of the cards. **`--q` repeated** answers several requests with one refresh of the index, a block `— «<запит>»` each (`meeting-processor`: the participants at once); CTX_RESULT then has `requests`.
- **Hints of a local index — since v3.18.1.** A registered local index that keeps its own `entities(key, kind, path)` and `edges(src, dst, kind)` is read as a hint, never a merge: two cards it files under one key that the plugin's keys keep apart are an open pair `можливо той самий: … (підказка <id>)`, closed by your `same`/`not-same` as any other; an edge from a note the plugin's own index does not hold — never the store, a blocks file or `_System/_scratch/` — is a `хто посилається` line with ` · <id>`, a sensitive one by the search's rules. Edges never decide an entity or a slot. A local index with no such tables says nothing; one whose tables have other columns says `<id>: підказок немає — незнайома схема` (once), one of whose two tables alone has them `<id>: таблиця <table> незнайомої схеми — без неї`. Only a local index's links count as backlinks (`wikilink`, `fm:<field>`), never its mentions or typed keys; a hint read cut short says `<id>: підказки прочитано не повністю (…)`. `--slot` with `pairs`, `same` or `not-same` is exit 3. A link's field is in the line (` · поле <field>`), under the rules of a sensitive note.

## 6. The context card

`INDEX.md`, at most 200 lines, regenerated by every compile that changed something: who the user is (name, role, language), onboarding (mode, deferred steps), products (Jira key, Confluence space, platforms), teams (member counts), vaults and providers, then one row per record — id, title, a one-line summary, the date of the last change. A longer table ends with `+N more — ctx list`. People and team-member names never appear (`people-context-protocol.md`): only counts. Since v3.13.0 one line `- **Repos:** <id>: <N> блок/блоки/блоків · v<version> · перевірено <date>; <id>: …` about the registered repositories that have blocks in the records, one entry each, joined by `; ` (the version is the one most blocks have a base at; `ctx provider apply`, `adopt --apply` and the daily sync refresh the line though no record changed), and a team's member count falls back to the table of the `team` block when your own team section has none. Since v3.12.0 stale rows end with `⚠ <date>`, with a line counting them and one counting the archive; `ctx read` opens with the card.

## 7. The session digest

With a store, the SessionStart digest adds one read-only line: `context: records N · card M lines · in sync` — or `· K edits to import`, or `· C conflicts (ctx sync)` (a record missing on disk counts as one) — plus `· K stale` when records are stale and `· N custom unassigned` when `custom` records have no `read_by` (since v3.12.1), and tells skills to run `ctx read --skill <name>` at Step 0c. A store used before that cannot be reached (a vault not mounted, moved or switched off) → `context: store at <path> unavailable — vault not mounted?`. It is read within a two-second budget so an iCloud download never holds the session start; no store, or any failure → no line (a count that only misses the budget shows the summary saved last — below). Since v3.16.0 one more line, `index: секцій N · оновлено <день>`, says what the search's section index holds — read from its `index.json` alone, within 0.2 s, never from the SQLite file; no index, or an `index.json` not read in time → no line. Since v3.13.0 the `providers:` line dates a repository by the store's last check of it when that is later than the registration's `synced_at`: the dates are read from `.state/blocks/` after the store's facts, with half a second of their own, so a block state that does not arrive (iCloud) costs the dates, never the `context:` line; the digest never goes to the network.

**On a cold start (since v3.13.1).** The live count gets two seconds; when it misses them (an iCloud download, an antivirus scan of the records), the digest shows the summary saved last instead, marked with when it was saved — `context: records N · card M lines · <tail> · cached YYYY-MM-DD HH:MM` — with its dates on the `providers:` line, and still tells skills to run `ctx read`. The summary lives in `~/.grow-pm/.ctx-summary.json` (§1): the digest writes it after every live count that came in time, and every writing `ctx` command that exits 0 writes it after its run (a failure to save never changes the exit code); reading commands never write it. A summary older than 7 days, saved for another context file, not JSON, of another schema or without the counts is not used — no line, as before; a live count that fails in time (no store, an error) gives no line, and the cache never stands in for it. The digest still never goes to the network, and reads the provider registrations within one second each and two seconds for all of them (since v3.14.0; several evicted files never cost the hook a second apiece) — one that does not arrive is named on the `provider registration unreadable` line as `not available locally (still downloading?)`. `ctx` reads them within three seconds each and six for all of them (since v3.14.0) in `repo list`, `repo status`, `provider adopt|plan|apply|sync`, `read` (the line naming a block's repository) and for the card's `Repos` line (every compile, `card`, `migrate --apply`). A registration it could not read is named only here: `repo list`, `repo status` and `provider plan|apply` without a repository print `unreadable registration: <path> (<reason>)` (and list it under `unreadable` in `CTX_RESULT`); `provider adopt|plan|apply` that name a repository and do not find it add `— a registration could not be read: <path> (<reason>); it may still be downloading` to the usage error; the card keeps the `Repos` line it has rather than rebuild it from a partial list (after an adopt that wrote or an apply: `card not refreshed: a registration could not be read: …`). `read` is quiet about it: it leaves the registration out of that line without a word — the line naming a block's repository is not worth failing a read. A writing command's summary is counted on the digest's budget (two seconds, then half a second for the days of the last checks): a count that misses it saves nothing and the summary saved before stands, and days that miss keep the days saved before. The same six seconds are the provider boundary's for a writing command (§3) and for the write gate (`scripts/write_gate.py`), which asks for confirmation — naming the registration — when one was not read in time, because the target may lie in that provider's folder.

**The `repos:` line (since v3.14.0).** For the repositories whose registration says `sync: daily` and is not paused, the digest adds, right after the `context:` line, one line with the last result of their daily sync (§12.11 of the provider protocol), read from the block state with the days of the last checks — on their half second — or, on a cold start, from the saved summary, which carries the results too. Parts are joined by `; `, at most three, the rest `+N`; a part with a zero is left out; a repository whose sync was switched off or is paused shows nothing, and with no `sync: daily` repository there is no line. The one text that comes from outside is the reason of a broken source or an error, with its control characters stripped and clipped to 80 characters.
- `  repos: <id> · synced <YYYY-MM-DD> · <U> updated · <K> conflicts kept yours · report <path from the storage root>` — a pass that changed blocks (`<U>` = updated + added + removed; `<K>` the conflicts where your text was kept; `1 conflict kept yours` in the singular); a day with a report but no change still names the report
- `  repos: <id> · synced <YYYY-MM-DD> · no changes`
- `  repos: <id> · synced <YYYY-MM-DD> · ⚠ source behind — nothing taken · no changes` — a pass over a copy older than your bases (`held_behind`): nothing of it was taken, and the mark stays as long as the copy lags (the report names the blocks once); the mark comes right after the date in a `changed` part too
- `  repos: <id> · unreachable since <YYYY-MM-DD> (VPN?)` — the day of the last successful check
- `  repos: <id> · ⚠ <N> removals held — ctx provider plan <id>`
- `  repos: <id> · sync timed out <YYYY-MM-DD>`, `· ⚠ source broken — <reason>`, `· ⚠ edits to import first — ctx sync`, `· ⚠ sync error — <reason>`
- any of them ends with `· <N> block(s) awaits a decision` when a `?` waits — a `?` held because the source lags counts too

The digest's `Skills:` line names `ctx provider sync --if-due` before `ctx read`, and asks the skill to repeat any line it prints that starts `Ядро оновило` at the end of its answer — the line for a skill that takes the short path through the digest (Step 0c of `local-context-protocol.md` is the same instruction for a host without the digest).

## 8. Snapshots and the journal

- A snapshot holds the records, the state (its subfolders too, such as `.state/blocks/` since v3.13.0; `.state/slots.json` since v3.15.0, so `ctx undo` brings your decisions about slots back with the rest; and `.state/search.json` since v3.16.0, your choices in the search; `.state/entities.json` since v3.18.0, your answers about entities), the card and both copies, with a manifest and a content hash; an identical newest snapshot is reused. Rotation: the last 20 plus the newest of each day for 14 days. The pre-migration and pre-apply backups in `~/.grow-pm/backups/` (last 5, `persistent-storage.md`) are separate and unchanged.
- `journal.jsonl` — one JSON line per change: `ts`, `op`, `ids`, `source`, `reason`, `snapshot`. A provider pass adds `op` `provider-apply` (with `from_v`, `to_v`, `decisions`, `pending` and, since v3.14.0, `taken` — the repository texts the pass wrote into your records: `{block: hash}`, or `"removed"` for a block it removed), `provider-sync` (a pass of the daily sync: the same line, the same snapshot label) or `provider-adopt`, `source` `repo:<id>`. A `ctx slot …` command (since v3.15.0) adds `op` `slot` with `action` (`bind`, `map`, `prefer`, `decide` or `forget`) and `slot`, `ids` empty, `source` `ctx-slot` and the snapshot taken before it wrote `.state/slots.json`. `ctx search remember|forget` (since v3.16.0) add `op` `search` with `action` (`remember` or `forget`), `q` (the request), `product`, `ids` empty, `source` `ctx-search` and the snapshot taken before it wrote `.state/search.json`. `ctx entity same|not-same` (since v3.18.0) adds `op` `entity` with `action` (`same` or `not-same`), `cards` (the two paths), `ids` empty, `source` `ctx-entity` and the snapshot taken before it wrote `.state/entities.json`.
- **One snapshot and one journal line per repository.** A `provider apply` over several repositories takes them one after another, so `ctx undo` takes back the last repository's pass only; `ctx undo --steps N` goes back N passes. A crash between the record writes and the journal line leaves the records changed and a snapshot with no journal line: `ctx undo` follows the journal and steps back to the operation before it, so run `ctx provider plan` again — it reads the records as they are.
- **Undoing a pass of the daily sync (since v3.14.0).** `ctx undo` takes a `provider-sync` pass back like any other change: records, state and compiled copies. It also makes the sync remember the pass as rejected: for every block the pass took (`taken`), the repository's text — its hash, or `"removed"` — goes into that repository's block state as `rejected` (the last ten per block), written after the restore so that the restore does not erase it. Neither the sync nor a manual `provider apply` applies that text again; the block stays held (`утримано`) until the core publishes something else in it, or until you take it yourself with `--choose <block>=theirs`. The command prints `не застосовуватиметься, доки ядро не змінить блок: <repo>: <blocks>`, and `CTX_RESULT` carries `rejected` (`{repo: [blocks]}`) and `rejected_failed` (`{repo: why}`, for a state that could not take the memory — the undo stands, and a line says the sync may apply the text again). Only a `provider-sync` line counts: undoing a manual `provider apply`, an import or any other change remembers nothing. The reports in `sync/` are not part of a snapshot and stay.
- **One block, not the whole pass.** `ctx undo` takes back the last change in the journal, not a named snapshot, so once anything was written after the sync pass it takes that back first. To change one block, prefer `ctx provider apply <repo> --choose <block>=theirs` to `ctx undo`: it takes the core's text for a block the sync left as yours — the report prints the command ready under a conflict kept as yours, but not under one where the core removed the block — and a block the sync updated that you want in your own words you simply edit: an edit inside a block is kept (§5e).
