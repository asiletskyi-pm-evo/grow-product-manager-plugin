# product-landscape — дизайн-спека (v3.3.0)

**Дата:** 2026-09-11 · **Статус:** погоджено в чаті, очікує план реалізації · **Цільовий реліз:** v3.3.0 (після v3.2.0) · Англійська версія (канонічна для реалізації): `2026-09-11-product-landscape-design.md` · Пов'язані: `2026-09-10-flow-walkthrough-design.md`, `2026-09-11-test-accounts-and-legs-design.md`.

## 1. Проблема і мета

Плагін знає конкурентів користувача як плоский список у `local-context.md` (`product.competitors`). Він не знає, які застосунки користувач встановив для вивчення, які продукти дотичні, а не прямі конкуренти, що кожен із них собою являє (категорія, платформи, поверхні для проходу, розмір) і які з них уже досліджені. Користувач вивчає цілу категорію (для Prom — десятки Shopping-застосунків з App Store) і хоче, щоб плагін **сканував, шукав, категоризував, характеризував і вів реєстр** продуктів, застосунків, програм і сайтів — конкурентів і дотичних гравців його продуктів — та **ініціював крос-продуктові дослідження** з нього: те саме флоу на кількох продуктах, інсайти, ідеї та гіпотези з конкурентів і дотичних продуктів, за запитом користувача або як пропозицію від скіла.

## 2. Ухвалені рішення (разом із користувачем)

| # | Рішення | Вибір |
|---|---|---|
| D1 | Де | новий скіл `product-landscape` (CRUD реєстру, сканування, пошук, карта категорії, ініціація досліджень); інші скіли читають реєстр і *пропонують* запуски, ніколи не стартують самі |
| D2 | Форма | один **спільний реєстр** `~/.grow-pm/landscape/` із записом на кожен продукт/застосунок/сайт плюс **зв'язки** від кожного продукту користувача з роллю: `direct-competitor | adjacent | benchmark | inspiration`; `product.competitors` стає похідним (перший запуск імпортує його) |
| D3 | Сканування машини користувача | встановлені Mac-застосунки та iPhone-застосунки з Mac App Store, телефон/емулятор через adb, явні списки від користувача; **закладки браузера лише після явного «так» у кожному скануванні** (Chrome, Safari); історія — ніколи |
| D4 | Джерела пошуку | безкоштовна база: публічний App Store lookup/search API (жанр, рейтинг, кількість оцінок, розробник, доступність на Mac), сторінки Google Play через браузерні інструменти, WebSearch; опційні конектори за наявності: Similarweb, Semrush, Tavily (пошук на хостах без WebSearch), Mobbin, Lazyweb, Apify app-data (чарти Play/App Store, відгуки) |
| D5 | Опційні конектори, оголошені плагіном | `.mcp.json` отримує шість записів за URL: `lazyweb`, `similarweb`, `mobbin`, `semrush`, `tavily`, `apify`; кожен користувач підключає свій акаунт/ключ у хості; кожен скіл працює і без них |
| D6 | Вибір кандидатів для дослідження | **без фіксованого ліміту**: скіл ранжує і пропонує найкращих кандидатів (роль, збіг категорії, розмір, доступні поверхні, давність), користувач обирає будь-яку підмножину або називає інші продукти |
| D7 | Автореєстрація | будь-який продукт, з яким плагін взаємодіяв (прохід, compare, конкурентний аналіз, референс Lazyweb/Mobbin, на який користувач відреагував), додається в реєстр зі `status: auto` і зазначеним джерелом; користувач потім підтверджує, змінює роль чи архівує |
| D8 | UX підтвердження | результати scan/discover показуються батчами по 10–15 (як глосарій): користувач підтверджує, перекатегоризовує, ставить роль або відкидає кожен; нічого не стає `status: confirmed` без користувача |

Поза v3.3.0: періодичні пересканування і сповіщення про зміни, моніторинг цін, аналіз настрою відгуків по сторах (територія feedback-triage), автоматичне встановлення застосунків, створення акаунтів у конкурентів (ніколи).

## 3. Компоненти

### 3.1 Сховище — `~/.grow-pm/landscape/` (нове в `persistent-storage.md`)

```
landscape/
├── registry.yaml            # індекс: slug → {name, kind, category, status, links[], updated}
├── products/<slug>.md       # один запис на продукт (frontmatter + нотатки)
├── scans/<YYYY-MM-DD>-<source>.yaml   # сирі результати scan/discover, кандидати, рішення користувача
└── maps/<category>-<YYYY-MM-DD>.md    # відрендерені карти категорій (це ж артефакт research/landscape)
```

Frontmatter запису (`products/<slug>.md`):

```yaml
slug: product-1-competitor-a
name: "Competitor A"
kind: app | site | desktop | service
category: "Shopping"            # назва жанру App Store / Play або вільний тег
subcategory: "marketplace"      # вільні теги
markets: [xx, yy]               # ISO-коди країн
developer: "Company A"
platforms: [ios, android, web, macos]
surfaces:                       # що може проходити flow-walkthrough
  web_url: https://example.com
  ios_app_id: 000000000
  ios_bundle_id: com.example.app
  mac_available: true | false | unknown
  android_package: com.example.app
  desktop_bundle_id: null
size_signals:
  ios_rating: 4.7
  ios_ratings_count: 120000
  play_rating: null
  similarweb_rank: null         # лише коли конектор відповів
characterization:
  model: "C2C marketplace with escrow"
  audience: "…"
  key_flows: [search, product card, checkout, reviews]
  notable: ["stars first in the review form", "…"]
links:
  - product: product-1           # slug продукту користувача з local-context
    role: direct-competitor | adjacent | benchmark | inspiration
    note: "…"
sources: [{type: scan-mac | scan-adb | bookmarks | appstore-api | play-web | websearch | similarweb | semrush | lazyweb | mobbin | apify | user, ref: "…", date: 2026-09-11}]
status: candidate | confirmed | auto | archived
first_seen: 2026-09-11
last_researched: null
walkthroughs: []                 # run id з ~/.grow-pm/walkthroughs
```

Тип vault `landscape` → `Research/landscape/` (36 типів); вбудований шаблон `research/landscape-v1.md` (карта категорії: таблиця продукти × характеристики, рядки «ми проти них», прогалини, кандидати для дослідження). Дані реєстру — внутрішні (`data-policy.md`): лише локально; файли закладок читаються, ніколи не копіюються — зберігаються лише обрані кандидати.

### 3.2 Скіл `skills/product-landscape/SKILL.md` — режими

| Режим | Форма запиту | Що відбувається |
|---|---|---|
| `scan` | «просканируй мої застосунки», «які застосунки я встановив у категорії …», "scan my apps" | `scripts/landscape_scan.sh` перелічує Mac-застосунки (`/Applications/*.app`, bundle id), iPhone-застосунки на Mac (`/Applications/*.app/Wrapper/*.app/Info.plist`, bundle id), пакети через adb, якщо пристрій підключено; bundle id → App Store lookup (жанр, рейтинг, кількість, розробник); Mac-застосунки без запису в сторі → назва + припущення категорії; закладки — після згоди в цьому скануванні → домени; кандидати ранжуються за збігом категорії з продуктами користувача; батчі по 10–15 на підтвердження (D8) |
| `discover` | «хто конкуренти й дотичні у сфері …», "find competitors and adjacent products for …" | джерела за D4, дедуплікація за доменом / bundle id, кожному — пропонована роль; категорія і ринки продукту користувача задають запити; батчі на підтвердження |
| `add` / `update` / `characterize` | «додай продукт X у реєстр», «охарактеризуй X», «постав X як дотичний до Prom» | CRUD одного запису; `characterize` заповнює `characterization` зі сторінки продукту, лістингу в сторі, флоу Lazyweb/Mobbin, вебу — з джерелами |
| `map` | «карта конкурентів по категорії …», «покажи реєстр» | артефакт `research/landscape`: продукти × характеристики, продукт користувача виділено, прогалини, список «ще не досліджено»; публікується як у product-research або лишається локально |
| `research` | «досліди однакове флоу на конкурентах», «знайди ідеї у конкурентів для …», або прийнята пропозиція іншого скіла | ранжує кандидатів (D6) і просить користувача обрати або назвати продукти; далі чейнінг: те саме флоу на обраних продуктах → **flow-walkthrough** `compare` (конкуренти лише читання; невідомі продукти автореєструються, D7); кабінетне порівняння → **product-research** (competitive / ux-benchmark з реєстром як списком конкурентів); ідеї й гіпотези → **brainstorm-features** з посиланнями на записи реєстру; результати пишуть `last_researched` і `walkthroughs[]` назад |

Кроки: 0 (контекст + хост; APP-DRIVE потрібен лише для проходів у `research`) → 1 режим → 2 доступні джерела (спостережені конектори; одним рядком — які опційні джерела є) → 3 виконання режиму → 4 батчі підтвердження → 5 запис реєстру + файлу сканування → 6 артефакт (карта) або чейнінг. Проактивні пропозиції живуть у скілах-споживачах (3.4) як рядки чейнінгу.

### 3.3 Конектори (`.mcp.json`, `integration-strategy.md`, Setup Guide)

| ключ | URL | Для чого | Без нього |
|---|---|---|---|
| `lazyweb` | https://www.lazyweb.com/mcp | база продуктів, екрани, флоу, експерименти; референси на тертя в audit flow-walkthrough | без референсів |
| `similarweb` | https://mcp.similarweb.com/ | схожі сайти, ранг трафіку, перетин аудиторій → пошук + сигнали розміру | лише App Store API + веб-пошук |
| `mobbin` | https://api.mobbin.com/mcp | флоу / екрани / секції реальних застосунків → characterize, референси | пропуск |
| `semrush` | https://mcp.semrush.com/claude/v1/mcp | `competitors_research`, `domain_overview` → пошук за доменом | пропуск |
| `tavily` | https://mcp.tavily.com/mcp | веб-пошук і витяг на хостах без WebSearch (Codex, ChatGPT) | WebSearch у Claude; на інших хостах — списки від користувача |
| `apify` | https://mcp.apify.com | чарти, ранги, відгуки App Store / Google Play через app-data-актори (оплата за результат) | Play через сторінки в браузері |

Усі шість — за URL, `type: http`; ключі користувача живуть у конфігурації конекторів хоста, ніколи в плагіні. Таблиця 1a в `integration-strategy.md` отримує шість рядків (колонки namespace «TBD, доки не виміряно», крім `lazyweb` — виміряно на Cowork 2026-09-10). `validate-consistency.sh` перевірка 9 тримає `.mcp.json` ↔ таблицю в синхроні; лічильник компонентів стає «12 конекторів». Setup Guide: крок «Опційні дослідницькі конектори» (що дає кожен, що це платний/акаунтний сервіс, який користувач реєструє сам, як підключити, як перевірити).

### 3.4 Споживачі і local-context

- **plugin-configurator**: Extended-крок **Landscape setup** — типова згода на сканування закладок (`питати щоразу | ніколи`), імпорт `product.competitors` у реєстр як кандидатів `direct-competitor` при першому запуску, категорія-сід на продукт (`product.category`, напр. жанр App Store); окремо `add Landscape` / `налаштуй карту конкурентів`.
- **product-research**: список конкурентів для порівнянь береться зі зв'язків реєстру (ролі `direct-competitor` + `benchmark`), з фолбеком на `product.competitors`; нові конкуренти, знайдені під час дослідження, автореєструються (D7); після конкурентного дослідження пропонує `product-landscape research`.
- **flow-walkthrough**: кандидати для `compare` беруться з реєстру (`surfaces` визначають, що можна пройти); кожен пройдений продукт автореєструється з оновленням `walkthroughs[]`; референси в audit (Lazyweb/Mobbin) можуть автореєструвати згаданий продукт як `inspiration`.
- **cjm-research**, **brainstorm-features**: по одній пропозиції в чейнінгу — «прогнати той самий етап / пошук ідей на продуктах реєстру» → `product-landscape research`.
- `references/local-context-protocol.md`: `product.competitors` документується як похідний від реєстру, коли реєстр існує.
- Скрипти: `scripts/landscape_scan.sh` (хости з SHELL; по одному JSON-рядку на кандидата: джерело, назва, bundle id / домен, шлях) — на хостах без SHELL скіл просить користувача вставити список застосунків.

## 5. Ризики

Стори і веб-джерела мають умови використання — скіл користується офіційними API, конекторами і звичайним читанням через браузер, ніколи масовим скрейпінгом. Закладки — особисті: згода на кожне сканування, без сирої копії. Зростання реєстру: статус `archived` і фільтр за `status` тримають пропозиції релевантними; кандидати без дослідження понад 12 місяців позначаються як застарілі у `map`.
